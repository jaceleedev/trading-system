# 브로커 관측과 계좌 대조

이 화면은 증권사가 보고한 주문·누적 체결 관측과 저장된 계좌 보유 변화를 대조합니다. 주문을 전송하거나 실제 계좌를 고치지 않습니다. 모의 원장과도 별도이며, 누적 수량의 차이를 개별 신규 체결이나 판단별 수익 실적으로 바꾸지 않습니다.

## 화면에서 진행하는 순서

1. 상단에서 계좌 관측을 선택해 수집 대상 계좌를 명시합니다. 필요한 주문 생성일 범위를 확인하고 브로커 읽기 스캔을 작업으로 접수합니다. 작업 접수와 실제 수집 완료는 구분합니다. 네트워크 수집을 별도로 허용한 워커가 실행해야 새 관측이 생기며 기본 설정은 수집을 실행하지 않습니다.
2. 저장된 스캔 목록에서 계좌, 조회 시작·종료 시각, 요청 범위, 페이지 완결성과 누락·지원 한계를 확인합니다. 목록에 없다는 이유로 주문이 존재하지 않는다고 결론 내리지 않습니다.
3. 같은 계좌의 이전·이후 계좌 관측과 대조에 사용할 브로커 스캔을 명시적으로 선택합니다. 선택한 자료로 대조 결과를 계산하고 확인한 결과를 저장합니다. 계좌나 입력 자료를 바꾸면 이전 계산을 새 결과처럼 표시하지 않습니다.
4. 주문별 누적 관측 변화와 비용 정정, 출처 연결 상태, 설명되지 않은 보유 변화를 확인합니다. 미확인 금액은 그대로 남기며 KRW와 USD를 환산 없이 합산하지 않습니다.

## 조회 범위의 의미

`CLOSED`의 날짜 조건은 주문 생성 시각인 `orderedAt`의 KST 날짜 범위입니다. 최종 체결 시각인 `filledAt`의 기간 조회가 아닙니다. 기간 안에 체결됐더라도 생성일이 범위 밖인 주문은 조회 대상에 들어오지 않을 수 있습니다. 부분 체결 주문은 `OPEN`과 `CLOSED` 양쪽 관측에 나타날 수 있으므로 같은 주문을 별개의 거래로 중복 집계하지 않습니다.

페이지를 끝까지 읽었다는 표시는 지정한 요청 범위 안의 완결성입니다. 공식 API가 지원하지 않는 주문 유형이나 조회되지 않는 채널까지 계좌 전체를 확보했다는 의미는 아닙니다. 개별 API 호출은 순차 관측이며 원자적인 한 시점의 계좌 상태로 취급하지 않습니다.

공식 `OrderExecution`은 누적 체결 수량, 평균 체결 가격, 총 체결 금액, 총 수수료·세금, 최종 체결 시각과 결제일을 제공합니다. 조회 시점 사이에 누적 값이나 비용이 바뀔 수 있습니다. 관측 수량·금액·비용 변화는 누적 보고 값의 비교이며 그 자체로 개별 체결을 재구성한 기록이 아닙니다.

## 연결되지 않은 자료를 해석하는 방법

현재 조회 계약에는 개별 `fillId`, `clientOrderId`, 주문 발생원, 원주문·정정 연결 ID와 채널 정보가 없습니다. 판단이나 로컬 주문 의도에 연결되지 않은 주문은 **출처 미연결**로 표시합니다. 이를 수동 매매로 단정하거나 다른 프로그램의 주문이라고 추측하지 않습니다.

계좌 보유 수량의 변화가 선택된 주문 관측으로 설명되지 않을 수 있습니다. 조회 범위 밖의 주문, 지원되지 않는 자료, 관측 시점 차이 등을 확인할 필요가 있지만, 이 화면에서 원인을 임의로 확정하지 않습니다. 설명되지 않은 변화는 대조 결과의 미해결 항목으로 남깁니다.

관측 해시와 참조 연결은 로컬 자료의 무결성과 대조 입력을 확인하는 수단입니다. 공급자의 완전성, 개별 실제 체결, 주문의 발생원이나 손익 실적을 인증하지 않습니다.

## 오류와 재조회

작업 접수나 저장 응답을 받지 못하면 원래 요청의 내용과 식별자로 결과를 다시 확인합니다. 이전·이후 계좌 관측이나 스캔 선택이 바뀌어도 미확인 요청을 새 입력으로 덮어쓰지 않습니다. 조회가 실패하면 이전 자료를 최신 상태로 표시하지 않고 다시 읽을 수 있게 합니다.

합성 작업실에서는 합성 스캔과 대조 결과를 명확히 표시합니다. 테스트 관측을 실제 브로커 수집 또는 실제 투자 성과로 설명하지 않습니다.

## API·CLI와 저장

`GET /api/v1/broker/scans`와 `/{id}`는 저장된 스캔을 읽습니다. `POST
/api/v1/reconciliations/preview`는 명시한 계좌·스캔으로 결과를 계산하며, `POST
/api/v1/reconciliations`는 같은 입력의 결정적인 보고서를 저장합니다. 서버 저장은
`--jobs`에서만 가능합니다. CLI의 `trading broker scans`, `scan`, `compare`, `save`,
`reports`, `report`는 같은 오프라인 서비스를 사용합니다. 비교 입력 파일에는
`before_snapshot_id`, `after_snapshot_id`, 선택적 `before_scan_id`, 필수 `after_scan_id`,
`mode`를 명시합니다. `as_of` 생략 시 선택 자료의 마지막 관측·기록 시각을 사용합니다.

실제 읽기 작업은 `broker-sync` 종류로 접수합니다. `account_seq`, `mode=prospective`,
선택적 `from_date`·`to_date`·`symbol`, `max_pages`(1~10), `page_size`(1~100),
`detail_order_ids`(최대20개)를 받습니다. 기본 worker는 네트워크 작업을 실행하지 않습니다.
모든 GET은 기존 공유 호출 간격·작업 임대 검사를 통과합니다. 429 응답은 뒤의 요청을
중단하고 미해결 범위를 남깁니다. 작업 완료에도 `coverage_complete=false`일 수 있습니다.

관측·스캔은 `var/broker-observations`, 보고서는 `var/reconciliations`의 개인 불변
파일입니다. 개인 자료 백업 v4는 두 저장소의 원문·참조·재계산을 검증하며 v1~v3도
지원합니다. DB migration은 추가하지 않았습니다.

현재 고정 계약은 [토스 공식 OpenAPI](https://openapi.tossinvest.com/openapi-docs/latest/openapi.json)의
v1.2.15이며 원문 SHA-256은 `ebaf20df342270274a5f6f5ad3a3d3d67b0ce02f30977da84606f3654924103e`입니다.
기존 계좌 OPEN 계약은 변경하지 않고 별도 GET 계약으로 보존합니다.
