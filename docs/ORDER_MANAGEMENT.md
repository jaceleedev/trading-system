# 비활성 주문 전송과 로컬 주문 의도

이 기능은 저장된 자금 계획·자금 배정·주문 의도를 연결하고 요청 처리 상태를 보존합니다. 실제 증권사 주문 전송은 계속 비활성입니다. 화면에 실제 전송 버튼을 제공하지 않습니다.

## 화면에서 진행하는 순서

1. 상단에서 기준 계좌 관측을 명시적으로 선택합니다. 저장된 자금 계획의 계좌·기록 구분을 확인하고 하나의 대안을 선택합니다.
2. 그 대안에 연결된 활성 자금 배정을 선택하고 로컬 주문 의도를 저장합니다. 기본 요청은 지정가와 당일 유효 조건입니다. 실제 주문 계약이 지원하지 않는 수량·조건은 서버 검증에서 거부하며 수량을 임의로 반올림하지 않습니다.
3. 주문 의도의 각 항목과 전달 상태를 확인합니다. 준비, 전달 중, 응답 확인, 거부, 미확정, 중단은 로컬 요청 처리 상태입니다. 브로커가 보고한 주문·누적 체결 상태와 별도로 표시합니다.
4. 연결할 브로커 스캔이 있으면 명시적으로 선택해 관측을 적용합니다. 출처가 연결되지 않은 판단이나 요청만으로 실제 체결·손익을 만들지 않습니다.

주문 의도가 연결된 자금 배정은 일반 배정 해제 흐름에서 풀지 않습니다. 미확정 요청의 비용·보유 약정을 확인하기 전에 자금이 다시 사용 가능한 것으로 표시해서는 안 됩니다. 모의 매매 원장의 가정 체결과 이 주문 의도 관리도 별도로 유지합니다.

## 합성 응답 검사

합성 작업실에서만 승인 응답, 거부 응답, 응답 유실, 전송 전 실패의 준비된 상황을 선택해 상태 변화를 검사할 수 있습니다. 화면에서는 이를 **합성 주문 응답 검사**로 명시합니다. 이 동작은 실제 주문을 전송하거나 거래 성과를 확인하는 행위가 아닙니다.

응답 확인은 해당 요청에 대한 응답을 받았다는 뜻입니다. 실제 체결 여부와 누적 수량은 별도의 브로커 관측으로 확인해야 합니다. 응답을 놓쳤을 때는 성공이나 실패를 추측하지 않고 미확정 상태를 유지합니다.

## 정정·취소와 중단된 처리

브로커 주문 ID를 알고 있는 항목에서만 정정·취소의 로컬 의도를 접수합니다. 새 수량과 가격은 명시하고 기록된 조건을 보존합니다. 정정·취소 의도 접수는 브로커 정정·취소 완료를 뜻하지 않습니다.

중단된 전달을 복구할 때는 확인되지 않은 결과를 표시합니다. 실제 결과를 모르는 요청을 자동으로 재전송하지 않습니다. 재시도 버튼이 있더라도 저장 처리 결과를 같은 식별자와 원래 내용으로 확인하는 동작과 증권사 전송을 구분합니다.

화면에서 계좌·계획·예약·주문 선택을 바꿔도 이미 접수한 요청을 새 선택으로 덮어쓰지 않습니다. 늦은 응답이 현재 선택한 주문의 결과를 바꾸지 않도록 처리하고, 조회 실패 시 이전 상태를 최신 상태로 표시하지 않습니다.

## 관측과 금액의 의미

계좌 순번과 주문 ID는 식별자이며 숫자로 변환해 정밀도를 잃지 않습니다. 금액·수량은 소수 문자열을 유지하고, 미확인 값은 0으로 채우지 않습니다. 매수 가능 금액은 현금 잔고가 아니며 통화별 금액을 환산 없이 합산하지 않습니다.

브로커 관측은 [누적 대조의 조회 범위와 제한](BROKER_RECONCILIATION.md)을 따릅니다. 개별 체결 ID·주문 출처·정정 연결이 제공되지 않는 범위에서 추가 사실을 추측하지 않습니다. 로컬 요청의 무결성이나 상태 이력은 실제 주문 성공, 개별 체결, 손익 실적의 증명이 아닙니다.

## 계약과 현재 구현 범위

공식 [토스 OpenAPI](https://openapi.tossinvest.com/openapi-docs/latest/openapi.json)
v1.2.15의 생성·정정·취소 POST 계약을 기존 GET 계약과 별도로 고정합니다. 원문 SHA-256은
`ebaf20df342270274a5f6f5ad3a3d3d67b0ce02f30977da84606f3654924103e`입니다.
요청 준비기는 네이티브 MARKET·금액 지정·미국 소수 수량 매도도 검증하지만, 현재 계획을
주문 의도로 연결하는 흐름은 수량을 지정한 LIMIT/DAY입니다. 소수 수량 LIMIT은 임의로
변환하지 않고 거부합니다. 호가 단위 전체·현재 세션·종목 적격성·실제 공급자 수락은
이 정적 계약만으로 확인되지 않습니다. 미국 정정은 가격만, 국내 정정은 명시 수량이
필요합니다. 국내 정정 수량이 부분체결을 포함한 총량인지 잔량인지는 명세에 분명하지 않습니다.

생성 `clientOrderId`의 멱등성 보장은 10분이고, 정정·취소에는 같은 키가 없습니다.
로컬 요청 키는 원래 논리 요청과 응답을 보존하지만 증권사 전송의 정확히 한 번 실행을
증명하지 않습니다. 합성 어댑터의 일정한 응답 ID는 테스트 가정입니다. 실제 어댑터는
자격증명·HTTP 전송을 갖지 않고 항상 비활성 결과를 돌려줍니다. 별도 활성화 구현과
검증 없이 설정만으로 실제 전송을 켤 수 없습니다.

전달 전에 DB 상태와 토큰을 먼저 기록합니다. 같은 요청은 다시 전송되지 않으며,
전달 중 끊긴 처리는 명시적 복구로 미확정 상태가 됩니다. 늦게 도착한 응답의 ID 연결과
근거는 남겨도 자동 재전송이나 정산은 하지 않습니다. 새 응답 ID를 받으면 과거 ID의
관측을 새 주문 상태로 쓰지 않습니다. 같은 ID·같은 관측 시각의 다른 내용은 충돌입니다.

배정과 주문 의도의 연결은 DB에서 원자적으로 확인합니다. 연결 중인 활성 배정을
일반 자금 화면의 해제·교체가 풀지 못합니다. 현재 정정은 원래 항목의 수량과 필요
자금을 초과할 수 없으며 체결 예상 대금이나 추정 잔량으로 여력을 늘리지 않습니다.
한 번이라도 전달 처리를 시작한 의도의 배정은 이번 기능에서 정산·해제하지 않습니다.
처리를 시작하지 않은 의도 전체를 중단하면 연결만 해제하며, 원래 배정 해제는 별도
명시적 동작입니다. 주문 응답·취소·목록 부재만으로 현금이나 보유를 수정하지 않습니다.

## API·CLI와 복구 자료

`/api/v1/order-intents`의 목록·생성, `/{id}`의 상세 조회, `/{id}/modify`, `/cancel`,
`/abort`, `/recover`, `/observe`가 같은 서비스를 사용합니다. 합성 검사만
`/{id}/operations/{operation_id}/simulate`로 제공합니다. 입력의 요청 키와 현재 revision을
검사하고 실제 응답·전송 완료를 선언하는 사용자 JSON은 받지 않습니다.

CLI는 `trading orders create/list/show/modify/cancel/abort/recover/observe/simulate`이며
명시한 작업실의 로컬 DB만 사용합니다. 변경 입력은 `--input` JSON 파일, 의도 선택은
`--id`, 합성 실행 항목은 `--operation-id`로 지정합니다. 실제 전송 명령은 없습니다.

DB migration `d724b39a610e`는 주문 의도·처리·이벤트 세 테이블을 추가합니다. DB 백업과
계좌·계획·브로커 입력 파일 백업이 함께 필요합니다. 개인 파일 백업 v5의 성과 기록에
고정된 원장 발췌가 있어도 DB 운영 상태와 이력은 이 파일 백업만으로 복원되지 않습니다.
요청 결과·이벤트는 크기를 제한하고 상세 화면에는 최근 이벤트
100개와 생략 수를 표시합니다. 과거 사건의 기준시각과 새 조회 시각을 구분합니다.
